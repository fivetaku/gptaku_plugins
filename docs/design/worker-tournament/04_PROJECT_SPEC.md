# 프로젝트 스펙 — AI 행동 규칙

이 폴더의 문서를 근거로 작업하는 에이전트가 지켜야 할 규칙.

---

## 1. 절대 규칙

### 1-1. 품앗이에 토너먼트를 넣지 않는다

품앗이 SKILL.md의 명시적 전제 4개와 충돌한다 (01_PRD §2). "배관이 되니까 된다"는 근거가 아니다 — 품앗이의 정체성은 **분할**이고 토너먼트는 **중복**이다.

품앗이에서 하는 일은 grok을 `command` 문자열 프로바이더로 추가하는 것뿐이다.

### 1-2. 게이트 없는 토너먼트를 실행하지 않는다

`task.gates`가 비면 거부한다. 게이트가 없으면 채점이 모델 판정만 남아 재현성이 사라지고, 그러면 A/B 벤치(V5)의 결과도 신뢰할 수 없다.

### 1-3. 참가자 워크트리를 공유하지 않는다

참가자가 같은 디렉토리에서 돌면 서로의 파일을 덮어쓴다. `worktree` 경로 중복은 실행 전에 거부한다.

### 1-4. 병합 시 승자 코드가 베이스다

패자 워크트리를 통째로 덮거나 파일 단위로 교체하지 않는다. 이식은 델타 단위, 이식마다 게이트 재실행, 나빠지면 롤백.

### 1-5. 캐시 복사에 셸 글롭을 쓰지 않는다

```bash
cp -R "$SRC/."  "$DST/"     # ✅
cp -R "$SRC"/*  "$DST/"     # ❌ .claude-plugin/ 누락
```

복사 후 `trash "$DST/.git"` → `diff -rq "$SRC" "$DST" --exclude=.git`로 대조한다.

## 2. 코드 수정 규칙

### 2-1. 프로바이더 분기에는 실측 날짜 주석을 단다

저장소의 기존 분기(`run-cli-worker.js:77-105`)는 전부 실측 날짜와 관찰 내용이 주석으로 달려 있다. 새 분기도 같은 형식을 지킨다.

```js
// 실측(YYYY-MM-DD, grok 1.0.4): 비-TTY 파이프에서 stdout 정상 — agy의 누락 버그 없음.
```

기억으로 주석을 쓰지 않는다. 실제로 돌려본 것만 적는다.

### 2-2. `PROVIDER_BINARIES`와 usage 문자열을 함께 고친다

`run-cli-job.js`의 프로바이더 목록은 4곳에 흩어져 있다 (`:6`, `:25`, `:104`, `:110`). 하나만 고치면 도움말과 실제 동작이 어긋난다.

### 2-3. CLI 전용 플래그를 다른 프로바이더에 주입하지 않는다

`--output-schema`/`-o`는 codex 전용이라 `isCodex` 게이트가 이미 있다 (`pumasi-job-worker.js:243`). grok의 `--json-schema`도 같은 방식으로 grok에만 주입한다. 프로바이더가 모르는 플래그는 spawn 실패를 낸다.

### 2-4. 환경변수는 기존 네이밍을 따른다

`KKIRIKKIRI_CODEX_MODEL` → `KKIRIKKIRI_GROK_MODEL`.

## 3. 끼리끼리 Workflow 경로 규칙

Step 4-W의 기존 규칙은 **새 템플릿 5종 전부에 그대로 적용된다.**

| 규칙 | 내용 |
|---|---|
| 모델 핀 필수 | 모든 `agent()` 호출에 `model` 명시. 예외 없음 (상속 시 비용 폭증) |
| 팬아웃 본체 | `sonnet` (기본 — 망설여지면 sonnet) |
| 기계적 처리 | `haiku` (토너먼트 shim이 여기 해당) |
| 종합 | `opus`, 워크플로우당 1~2회 |
| adversarial-verify | 팬아웃 종합 전에 필수 |
| 구조화 출력 | 수집·검증 스테이지는 `schema` 강제 |

### 3-1. 토너먼트 shim

Workflow 스크립트에는 셸·파일시스템 접근이 없다. 외부 CLI에 닿는 유일한 경로는 `agent()`가 스폰하는 서브에이전트의 Bash다.

```
agent("run-cli.sh로 <provider> 실행, JOB_DIR 반환", {model: 'haiku', schema: {...}})
```

이 shim에 판단을 주지 않는다. 명령 실행과 경로 반환만 시킨다.

## 4. 검증 규칙

### 4-1. 실행 없이 완료를 보고하지 않는다

"설정했으니 될 것"은 완료가 아니다. 05_VALIDATION.md의 각 항목은 실행할 명령과 기대 출력이 적혀 있다. 그 출력을 실제로 본 뒤에만 통과로 기록한다.

### 4-2. 순서 형태는 타임스탬프로 증명한다

`serial`/`chain`/`fanout`이 실제로 순서를 바꿨는지는 `startedAt`/`finishedAt` 대조로만 확인한다.

### 4-3. A/B 벤치 기준은 실행 전에 고정한다

V5의 우위/동등/열위 기준을 벤치 실행 **전에** 확정한다. 결과를 본 뒤 기준을 정하면 사후 합리화다.

### 4-4. 비용을 통과율과 함께 기록한다

토너먼트는 N배 비용이다. 통과율만 적고 비용을 빼면 판정이 왜곡된다.

### 4-5. 반증도 기록한다

A/B 리포트에 판정에 유리한 관찰만 남기지 않는다. 반하는 관찰도 같이 적는다.

## 5. 판정 규칙 — 기능을 접을 수 있어야 한다

01_PRD의 가정 1("토너먼트가 단일 워커보다 낫다")은 **미검증 가설**이다.

V5에서 우위가 확인되지 않으면:
- Phase 4(병합)를 **착수하지 않는다**
- 토너먼트를 기본값으로 승격하지 않고 옵트인 실험 기능으로 둔다
- 열위면 동결하고 원인을 분석한다

기능을 완성하는 것이 목표가 아니라, 값을 하는지 확인하는 것이 목표다. 벤치 결과가 나쁜데 "그래도 만들었으니 넣자"로 가지 않는다.

## 끼리끼리: 핵심 판단

바로 전체 오케스트레이터를 다시 만드는 것은 권하지 않는다. 먼저 서로 충돌하는
지침과 실패 후 재작성 비용을 줄인 기준선을 만들고, 그 기준선과 비교해서
**한 가지 실행 경로의 검증된 실행 명세 생성**을 실험하는 것이 적절하다.

모델은 의도 파악·작업 분해·전문 판단을 담당한다. 결정론적 코드가 담당할 후보는
이미 결정한 내용을 카드·프롬프트·실제 실행 인자에 일관되게 반영하는 일이다.
지침이나 카드에 쓴 `read-only`를 실제 권한 강제로 포장해서는 안 된다.

아래 경로는 `plugins/kkirikkiri/` 기준이다. 이 문서의 설계는 제안이며 구현 상태가 아니다.

### 실험 기록에서 알 수 있는 것과 없는 것

`PRD/kkirikkiri-structural-team-builder/_experiment/verdict.md:169-175`의
v0.24.4 R4 기록은 Workflow 4회 모두 첫 스크립트가 린트에 막혔고,
Teams 4회 모두 경계 없는 스폰을 수정했다고 보고한다. 이는 게이트가 필요한
이유이면서, 올바른 첫 입력을 만드는 준비 단계에 개선 여지가 있다는 근거다.

같은 기록의 후기 동일 모델 비교에는 끼리끼리 14~21분과 품앗이 약 5분이 나온다.
그러나 각 조건 2회, 다른 동시성, 수동 품앗이 작업 지시와 자동 끼리끼리 기획 등
변수가 섞여 있다. 이를 현재 버전의 속도 차이나 Teams의 열세로 단정하지 않는다.
전체 중 카드 생성·재읽기·게이트 수정 각각이 차지한 시간은 아직 측정되지 않았다.

### 세 가지 선택지

1. **국소 정비만:** 질문·모드·리더·검토 정책을 일치시키고 예제와 세션 장부를 고친다.
   가장 작지만 모델이 매번 실행 규약을 조립하는 문제는 남는다.
2. **얇은 준비기 실험:** 선택지 1의 수정이 양쪽에 반영된 기준선에서, 한 가지
   실행 형태만 구조화된 launch record로 만들고 기존 실행 payload를 생성한다.
   권고하는 다음 단계다.
3. **호스트 공통 오케스트레이터 전면 개편:** 승인·메시지·권한·복구까지 다시 구현한다.
   현재 근거로는 비용과 회귀 위험이 크므로 보류한다. 품앗이의 Claude 워커 지원이
   이 전면 개편을 요구하거나 정당화하지 않는다.

### 권고하는 최소 실험

첫 실험은 독립 태스크의 기존 Teams 스폰 한 경로만 대상으로 한다.
새로운 서버나 공통 플러그인은 만들지 않는다.

모델이 결정할 내용:

- 사용자 목표와 non-goals, 태스크 분해, 의존성, 전문 지식과 위험.
- 팀원별 역할, 결과물, 실제 완료 기준, 미확정 결정.

코드가 검증·생성할 내용:

- run/session ID, 승인된 모드, 태스크별 모델·도구·쓰기 범위·중단 조건.
- 요구 필드 누락과 기계적으로 확인 가능한 충돌.
- 동일한 기록으로부터 카드 표시본과 스폰 프롬프트/실제 인자 생성.
- 명시된 제한과 실제 호스트가 강제한 제한의 구분.

초기 명세는 다음 정도로 제한한다:

```text
LaunchRecord:
  runId, sessionId, revision, approvedMode
  tasks:
    id, role, instruction, acceptanceIds, outputs
    model, declaredScope, runtimeRestrictions, stop
  approvalRevision
```

모드·쓰기 범위·역할·완료 기준이 바뀌면 기존 승인을 재사용하지 않는다.
표현만 바뀌는 재렌더와 실질적인 실행 변경을 구분해야 한다.
호스트가 지원하지 않는 제한은 조용히 흉내 내지 않고 설명하거나 실행을 중단한다.

완료 판정 정비는 준비기와 분리한다. 읽기 전용 조사, 정당한 무변경, 부분 완료,
실패를 별개 결과로 표현한다. `criterion -> evidence -> artifact identity` 정도의
작은 기록으로 시작하며 범용 provenance 시스템을 만들지 않는다.

### 효과 검증

- **준비 단계 A/B:** 동일하게 승인된 계획, 모델, 팀원 수, 실행 형태, 게이트를
  고정하고 기존 조립과 launch-record 조립만 비교한다.
- **전체 A/B:** 같은 원본 요청과 사용자 답변, 같은 저장소 기준선에서 시작한다.
- 측정: 첫 워커 시작 시간, 준비 토큰, 중복 읽기, 스폰 차단·수정 횟수, 리더 턴,
  최종 검증 비용, 전체 시간, 실제 범위 위반, 완료 기준 충족.
- 실패·타임아웃·재작업을 분모에서 빼지 않는다. 캐시·사용자 대기 시간은 분리한다.
- 개편이 빨라도 결과 품질·허용 범위·독립 검증이 나빠지면 채택하지 않는다.
  모델 변경이나 검증 배치 크기는 별도 요인으로 실험한다.

독립 비판 검토에서는 “모든 개선을 한 명세 시스템에 묶으면 또 다른 권위와
오케스트레이터가 생길 수 있다”고 지적했다. 따라서 국소 정비를 실험 양쪽의
기준선으로 먼저 적용하고, 구조화 준비기의 순수 효과만 검증하도록 권고를 좁혔다.

## 품앗이: 구현한 동작

- 호스트 선택: `--host` > `PUMASI_HOST` > `pumasi.host` > `claude-code`.
- Claude Code 호스트의 기본 워커는 기존 Codex. OMO/Codex/other 호스트의 기본
  워커는 `claude --print --permission-mode acceptEdits`.
- task.command와 명시한 defaults.command는 호스트 기본값보다 우선한다.
- 호스트와 확정 명령을 job.json에 저장하므로 다음 라운드·재위임 중 환경이
  바뀌어도 워커가 바뀌지 않는다.
- 비-Claude 호스트는 프로젝트의 `.pumasi/jobs`를 기본 저장 위치로 쓴다.
- Claude 프롬프트는 stdin으로 전달한다. runner가 JSON/schema 출력과
  no-session-persistence를 설정하고 model/tool/permission 옵션은 보존한다.
- Claude의 structured_output을 기존 report.json 계약으로 정규화한다.
  잘못된 출력·API 오류·partial·failed·timeout·취소는 done으로 승격하지 않는다.
- stdout/stderr가 모두 저장되고 보고서 처리가 끝난 후 완료 상태를 기록한다.
- 기존 Codex/Grok/agy/gjc/Cursor 호출과 compact 결과·공통 게이트 동작은 보존한다.
- 다른 호스트에서는 Claude 전용 설치 훅을 실행하지 않는다. 직접 Node 사용이며,
  OMO 마켓플레이스 플러그인 형식으로 별도 설치한 것은 아니다.

## 실제 OMO -> Claude 구현 검증

설치된 Claude Code 2.1.259의 help 및 실제 print JSON 호출을 확인했다.
먼저 도구 없는 구조화 응답으로 result/structured_output 형식을 확인한 뒤,
OMO에서 품앗이 start를 통해 제한된 실제 Claude 워커를 시작했다.

위치: `.omo/evidence/pumasi-host-smoke/`.

워커에 제공한 권한은 Read/Write/Edit이며 Bash는 제공하지 않았다. 모델은
명시적으로 sonnet을 선택했고, 인증·설치 설정은 변경하지 않았다. 이 테스트에서만
사용자 hooks/MCP 자동 실행을 끄고 기존 인증을 사용했다.

1. OMO가 함수 요구사항과 완료 기준을 작성했다.
2. 품앗이가 Claude Code를 별도 비대화형 워커로 시작했다.
3. Claude가 `duration.cjs`, `duration.test.cjs`를 실제로 작성했다.
4. Claude는 shell 권한이 없으므로 테스트는 호스트가 실행해야 한다고 보고했다.
5. OMO가 품앗이 gates로 node:test를 실행했고 5개 테스트가 모두 통과했다.
6. compact 결과에서 report·상태·게이트를 확인했다.

실행 JSON 기준: 22,823ms, 4턴, is_error=false, permission_denials=[].
주 구현 모델은 claude-sonnet-5였고 envelope에는 보조 haiku 사용도 기록됐다.
CLI가 보고한 비용은 $0.1405002이며 구독의 실제 추가 결제액을 뜻한다고 단정하지 않는다.

## 검증과 한계

- 실패 기준선: 신규 테스트 16개 중 14개 실패, 2개 기존 override 보존 통과.
- 현재 Node 회귀: 33개 통과. 호스트 우선순위, 혼합 명령, config 전달, 이후
  라운드·재위임, 대용량 출력 drain, timeout, host stop, 오류 봉투·부분 완료,
  기존 compact/shared gate가 포함된다.
- 기존 워커 명령 검사 18개 통과.
- 실제 구현 게이트 5개 통과.
- JavaScript/YAML 언어 서버가 설치돼 있지 않아 node 문법 검사·네이티브 테스트·
  YAML 파싱으로 확인했다. 진단 억제나 새 도구 설치는 하지 않았다.
- acceptEdits는 모든 Bash 명령의 자동 승인이 아니다. 호스트가 적절한 명시적
  도구/권한 정책을 선택하고 거부 결과를 확인해야 한다.
- 실제 생성 예시는 명시한 sonnet/도구 정책의 한 워커 검증이다. 모든 모델·호스트
  조합의 품질·비용·동시성을 보증하지 않는다.
- stop/timeout은 기존 기록 PID 기준이며 자손 전체 격리나 queued 취소를 새로
  보장하지 않는다. native Windows는 실제 실행하지 않았다.
- 마켓플레이스 18개 항목, 커맨드 29개, 스킬 계약 28개 검사가 통과했다.
  마켓의 기존 미등록 크롤러 경고는 유지되며 새 공개 등록은 하지 않았다.
- 독립 검토는 문서화한 호스트 실행 흐름을 승인하고 비차단 경계 두 가지를 지적했다.
  설정 파일 host만 사용한 암묵적 최근 작업 조회와, SIGTERM을 처리한 뒤 정상 종료한
  워커의 취소 판정이다. 두 경우를 실패 테스트로 재현한 뒤 보정했다.
- 최근 작업 조회에도 설정 host를 반영한다. stop은 신호 전에 취소 의도를 기록하고,
  워커는 출력 정규화 전에 그 기록을 확인한다. 새 시도는 이전 취소 기록을 제거한다.
  취소 의도를 최종 처리 전에 관측한 경우에 적용되는 보장이며 자손 격리를 뜻하지 않는다.
- 보정된 두 경계의 후속 독립 검토는 APPROVE다. 두 기존 지적은 해소됐고 새로
  확인된 차단 회귀가 없다고 판단했다. 검토자는 실제 코드·테스트를 읽었으며
  테스트나 유료 Claude 호출을 다시 실행한 것은 아니다.
- 원본 main은 `463544e42720e0e442a310e3bc78673ffd33be77`에 그대로 있다.

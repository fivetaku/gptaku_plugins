# gptaku 플러그인 질문 설계 정책 (Questioning Policy)

> 근거: 딥리서치 2회(소크라테스식 + 다양한 질문법) + A/B 시뮬레이션 3회(show-me-the-prd / kkirikkiri / vibe-sunsang / git-teacher).
> 적용 범위: Claude Code와 Codex 양쪽. 같은 SKILL.md를 두 하네스가 읽으므로 질문 도구만 §7대로 갈라 쓴다.
> 주의: A/B는 LLM 시뮬레이션·페르소나 n=1/셀·심판 1명 → **방향성 근거**(확정 통계 아님). 단 유형마다 일관된 방향을 보임.

---

## 0. 한 줄 원칙

**추론 가능한 건 묻지 말고, 물을 땐 사용자가 진짜로 도달(니즈/통찰/이해)할 때까지 — 단 이미 도달했거나 직접 답을 원하면 즉시 멈춰라.**

질문 설계의 핵심 트레이드오프는 **깊이 ↔ 마찰**이고, 마찰의 진짜 비용은 "답변 품질"이 아니라 **이탈**이다.

---

## 1. 공통 규칙 (모든 인터뷰형 플러그인)

1. **묻지 말고 추론** — 최초 입력·맥락에서 추론 가능한 건 질문하지 않는다. 물어야 하면 "기본값 제시 + 확인"으로(예: "모바일 앱으로 가정할게요 — 아니면 말씀 주세요").
2. **핵심 먼저, 한 번에 하나** — 정보가치 가장 높은 질문을 앞에(뒤로 갈수록 답이 짧고 균일해짐=satisficing). 열린 질문은 한 번에 하나. (단순 "분류/설정 고르기"는 객관식 카드가 더 낫다.)
3. **과거 행동 > 가정** — "이 기능 쓰실래요?"(가정·X) 대신 "지금은 이 문제를 어떻게 해결하세요?"(과거 실제 행동·O). [The Mom Test]
4. **"왜" → "무엇/어떻게"** — "왜 그랬어요?"는 방어를 유발. "거기서 무엇을 하려던 거였어요?"로.
5. **답을 되짚어라(반영)** — 다음 질문 전에 직전 답을 한 문장으로 반영. 신뢰↑·마찰↓. [OARS]

## 2. ★ 종료 규칙 — 가장 중요하고 가장 어려운 부분

학계에도 검증된 "언제 멈출지" 형식 규칙이 없다. 우리 A/B가 준 운영 규칙:

### 2a. 조기 종료 금지 (모든 new 설계의 #1 실패 모드)
- **첫 답변에서 끊지 마라.** 사용자가 표면적·예의상·회피성으로 답하면 그걸 결론으로 채택하지 말 것.
- 사용자가 **진짜 결과**(real need / 스스로의 통찰 / 실제 이해)에 **본인 발화로 도달**할 때까지 턴을 이어간다. 에이전트가 "이해했다"고 단정하는 건 금물.
- **간결함은 "사용자 확인"에 종속된다.** 마찰 최소화가 과해지면 도달 직전에 끊긴다.

### 2b. 회피 대응
- 사용자가 deflect하면, **다음 질문은 반드시 구체/과거행동 앵커**로(또 다른 추상 질문 X). 예: "그냥 현황 파악…" → "최근에 누가 '이거 어때' 물었던 게 언제였어요?" [kkirikkiri v2 검증]

### 2c. 과잉 가드 (역방향 — 2a와 균형)
- 사용자가 **이미 스스로 진단**했거나, **요청이 이미 충분히 구체적**이거나, **직접 답/명령어를 명시적으로 원하면** → 더 캐묻지 말고 **즉시 제공**하라. 과잉 질문/코칭/교육 = 마찰 실패. [k6-clear / p4-aware / p3-pragmatist 검증]
- 구분 신호: 답이 *표면/회피* → 더 (2a/2b). 답이 *진짜 도달/직접 요청* → 멈춤(2c).

## 6. ★ 선초안 원칙 (Draft-First) — 산출물이 문서/계획인 플러그인

> 근거: gjc(gajae-code) deep-interview 분석 + A/B 검증(2026-07-06, 히든 트루스 8항목×페르소나 3종×2변형,
> 사전 등록 기준 4/4 충족 — 포착 6.0 vs 5.0, 잔존오류 0.67 vs 2.0, 응답수 3.33 vs 5.33, 앵커링 미검출).
> 상세: `docs/interview-redesign-2026-07-06.md`, `docs/reports/interview-ab-2026-07-06.md`.
> 핵심: 초안이 가장 좋은 질문 생성기다. 백지 질문은 탐색적(넓고 얕음), 초안 기반 질문은 진단적(좁고 깊음).

### 6a. 초안이 질문보다 먼저
핵심 문제(§2a)가 잡히면, 남은 사양을 질문으로 채우지 말고 **즉시 초안을 쓴다.**
사양 질문은 초안 작성 전 1콜(최대 4문항)로 방향을 가르는 결정만 배치한다.
§2a와의 관계: §2a는 *문제 발굴* 단계(깊게), §6은 그 이후 *사양 확정* 단계(초안으로) — 충돌 아님.

### 6b. 사실 vs 결정 (질문 자격 심사)
- **사실**(현재 스택, 버전, 기존 패턴, 외부 API 제약, 시장 관행) → 묻지 않는다.
  조사(코드/웹)해서 "~로 확인됨, 근거: X"로 인용 확인만.
- **결정**(목표, 범위, 트레이드오프, 원하는 동작) → 사용자에게. 애매하면 결정으로 취급.

### 6c. 가정 원장 (assumption ledger)
작성 중 만난 미확정 지점은 둘로 분류:
- **blocking** (산출물의 구조를 갈라놓음) → 질문 큐에 적립
- **non-blocking** → 시장 일반 관행 기준 기본값 채택 + 원장에 기록 (문서 내 `> ⚠️ 가정:` 표시 + 목록화)

### 6d. 체크포인트 배칭
큐가 쌓이면 자연스러운 중간 지점(초안 완성 직후 확인 카드)에서 1콜로 배치 질문 — **최대 1회.**
작성 도중 산발적으로 질문을 던지지 않는다 (사용자를 터미널에 묶는 것 자체가 마찰).

### 6e. 납품 시 일괄 확인
초안과 함께 확인 카드(데이터 구조·단계 분리 preview + 임팩트 큰 가정 1~2개)를 제시하고 한 번에
교정받아 반영한다. 확인받지 못한 원장 항목은 **잔여 가정 목록**으로 납품물에 남긴다
(A/B 관측: 어떤 인터뷰 구조로도 못 잡는 잠재 항목이 존재 — 목록이 유일한 방어).

### 6f. 예산
납품 전 질문 총량: **열린 탐침 1회(§2a 재탐침 +1) + AskUserQuestion 2콜(콜당 ≤4문항).**
초과가 필요해 보이면 질문 설계 실패다 — 기본값+원장으로 돌려라.
예외: 사용자가 명시적으로 깊은 인터뷰를 요청한 경우만 예산 해제.

## 7. ★ Codex에서 질문하기 (같은 스킬을 Codex가 실행할 때)

플러그인 하나가 Claude Code와 Codex에 함께 깔린다. Claude Code에서는 지금처럼 `AskUserQuestion`으로 묻는다.
Codex에는 `AskUserQuestion`이 없으므로 아래 순서로 고른다. 도구가 있는지는 **이번 세션의 도구 목록**으로 판단한다 —
Codex 질문 도구는 공식 문서에 거의 없는 실험 도구라 모델·버전에 따라 빠질 수 있으니 있다고 가정하지 않는다(2026-11-23 오너 결정).

| 순서 | 조건 | 쓰는 것 |
|--|--|--|
| 1 | `request_user_input_async`가 도구 목록에 있다 | 이 도구로 묻는다. 곧바로 `{"accepted":true}`가 돌아오고 답은 **다음 사용자 메시지**로 온다 |
| 2 | Plan 모드이고 `request_user_input`이 있다 | 이 도구로 묻는다. 답이 올 때까지 기다린다. 1콜 1~3문항, 문항당 선택지 2~3개 |
| 3 | 둘 다 없다 | 채팅에 번호 선택지 블록을 내고 답을 기다린다(아래) |
| 4 | 사람이 답할 수 없는 실행(`codex exec` 등) | 묻지 않는다. 기본값으로 진행하고 가정을 기록한다 |

**옮기는 법**
- `AskUserQuestion` 1콜(≤4문항)은 `request_user_input_async` 1콜로 묶는다. Plan 도구는 3문항까지라 넘으면 나눈다.
- async 호출 형식은 하나뿐이다: `{"questions":[{"title":"헤더 — 질문","options":["추천안 (추천) — 설명","대안 — 설명"]}]}`. `question`·`header`·`id`를 넣으면 파싱 오류가 난다(2026-11-23 실측 4건 중 3건). 질문하는 스킬은 이 한 줄을 SKILL.md에 그대로 둔다.
- Plan 도구는 `header`(12자 이내)·`question`·`id`(snake_case)와 선택지 `label`·`description`을 쓰고, 추천 라벨 끝에 `(Recommended)`를 붙인다.
- 추천안을 첫 선택지에 둔다. "기타"는 넣지 않는다(두 도구 모두 자유 입력 칸을 붙인다).
- `preview`는 보여 줄 곳이 없으므로 도구를 부르기 직전 채팅에 짧은 예시(ASCII 관계도·표)를 먼저 쓴다. `multiSelect`는 제목 끝에 "(여러 개면 쉼표로)"를 붙인다.
- async를 부른 뒤에는 "위 질문에 답해 주시면 이어서 진행합니다" 한 줄만 쓰고 턴을 끝낸다. 답에 달린 결정을 추측으로 먼저 진행하지 않는다.
- 선택지가 없는 열린 질문(Turn 1 탐침 등)은 도구 대신 평범한 채팅 질문으로 묻는다.

**번호 블록 폴백(3번)**
```text
질문: <한 줄 질문>
1. <추천안> — 무엇인지, 트레이드오프
2. <대안> — 무엇인지, 트레이드오프
3. 문장으로 직접 수정 요청
```
추천안은 항상 1번. 여러 문항이면 Q1·Q2로 묶어 한 메시지에 내고 "Q1-1, Q2-2"처럼 받는다. "모르면 1번으로 진행하겠습니다"를 한 줄 덧붙인다.

**스킬에 넣는 것** — 질문하는 스킬의 SKILL.md에는 짧은 "실행 환경" 블록(위 4단계 한 줄 요약 + async 형식 한 줄)만 두고, 그 스킬만의 Codex 차이(경로·생략 단계·도구 이름)는 `references/codex.md`로 뺀다. SKILL.md가 Codex 설명으로 길어지지 않게 한다.
